# 当前履带速度请求与驱动反馈协议

版本：`foc-drive-feedback-v1`（2026-10-20）

本文件是当前两块 FOC 板与上位机之间的速度请求和只读电机反馈合同。它与旧 RevE `torque + speed limit` 命令不同；不得把策略输出的左右履带速度解释成转矩请求或绝对限速。旧文件仅作历史参考，不作为当前实现入口。

## 当前硬件资源与落地范围

当前两块 G431 FOC 板各驱动一台 BDUAV N5065、270 KV、7 极对电机。当前原理图已布置 TCAN1042 CAN 收发器、三相低边电流采样放大器到 MCU ADC 的路径、三路 Hall 输入；因此只读速度/电流反馈可复用现有连接。本次没有修改原理图或 PCB，也没有增加 FOC UART。IMU 与云台遥测由上位机从原有接口采集。

原理图连接表明确 `SO_U/V/W` 分别进 MCU ADC，`J_CAN` 提供 GND/CANH/CANL，`J_HALL` 提供三路 Hall；`R_CAN_TERM` 的 120 Ω 位当前 DNP，终端电阻需按线束拓扑在总线两端装配。Hall 连接有直通/分压选择，但已确认的 Hall 电压输出类型仍未实测，需到货核对后选路径。静态原理图连通不能证明 CAN 线束/终端或 Hall 电平已完成实体验收。

这些原理图连接只说明信号路径存在。当前模块没有可构建的 G431 FOC/HAL 源码，尚未实现 Iq/RPM 状态帧发送、boot epoch 生成、CAN 接收、速度环或 PWM 输出。三相采样要成为可信的有符号 Iq，还需由后续目标固件完成采样校准、角度变换与质量判定；Hall/RPM 也需在实体电机上校准方向、相序和低速质量。本文新增 C 程序只提供主机可执行的报文编解码和会话状态校验，不能代表目标固件或实机验证。

单点测得的 `Iq_A` 是 FOC 电流采样转换得到的 q 轴电流量，不是电池电流、轴转矩、履带接地力或真实力传感器输出。BMS 的电池电流、电压和功率预算继续由既有 BMS 接口独立提供；本协议不替代、不放宽既有 BMS 限流、硬件过流、母线过压、门极关断或重新 ARM 条件。

## CAN 物理帧约定

- 经典 CAN、11-bit 标准标识符、DLC 固定为 8；拒绝扩展帧、远程帧及其它 DLC。
- 每个报文末尾 `data[6..7]` 为 CRC16 小端序。CRC 使用 CRC-16/CCITT-FALSE：poly `0x1021`、init `0xFFFF`、无反射、xorout `0x0000`。
- CRC 覆盖顺序为 `CAN_ID低字节、CAN_ID高字节、DLC字节、data[0..5]`。CAN ID 的高字节仅含标准 ID 的有效位。
- 节点后缀 `N=1` 为左驱动器，`N=2` 为右驱动器。所有整数均小端序；有符号值为二进制补码。
- 当前协议版本由下面的 ID 家族隐含为 v1；没有单独的速度帧 version 字节。

| 用途 | ID（左 / 右） | 方向 | `data[0..5]` |
|---|---|---|---|
| Boot epoch 广播 | `0x4D1` / `0x4D2` | 驱动器→上位机 | `boot_epoch:u32`, `reserved:u16=0` |
| BEGIN | `0x4E1` / `0x4E2` | 上位机→驱动器 | `boot_epoch:u32`, `session_id:u16` |
| CLOSE | `0x4F1` / `0x4F2` | 上位机→驱动器 | `boot_epoch:u32`, `session_id:u16` |
| 速度请求 | `0x501` / `0x502` | 上位机→驱动器 | `session_id:u16`, `command_seq:u8`, `target_motor_rpm:i16`, `ttl_10ms:u8` |
| 电机状态 | `0x521` / `0x522` | 驱动器→上位机 | `sample_seq:u16`, `mechanical_rpm:i16`, `Iq_cA:i16` |
| 质量状态 | `0x541` / `0x542` | 驱动器→上位机 | `sample_seq:u16`, `device_tick_ms_low16:u16`, `quality_flags:u8`, `applied_command_seq:u8` |

### 会话与速度请求

`boot_epoch` 必须由目标平台在每次启动时提供非零、对本驱动器不复用的 32-bit 值。设备广播当前值；上位机必须先收到当前启动周期的值，再把该值放入 BEGIN/CLOSE。目标固件只接受与当前 `boot_epoch` 匹配的管理帧。若平台尚不能产生可保证不复用的 boot epoch，则必须拒绝 BEGIN，不能退化成接受没有 epoch 的速度请求。boot epoch 来源与生成目前待目标平台接入；本主机库不会生成或持久化它。

每次 BEGIN 使用非零 `session_id`。同一活动会话的重复 BEGIN 是幂等操作，不能清空命令序号或让旧序号重放。活动会话收到不同 token 的 BEGIN 必须拒绝；先收到匹配的 CLOSE 才能建立新会话。一个 boot epoch 内 `session_id` 严格递增、不复用且不回绕；达到 `0xFFFF` 后需等新的 boot epoch。匹配的重复 CLOSE 可幂等确认。速度请求必须带当前活动 `session_id`，其它会话的帧一律丢弃。

`command_seq` 是每会话内 8-bit 递增序号，模 256 前进；仅接受相对最后接受值前进 1–127 的新序号。重复、旧序号和半区间外的乱序值拒绝。会话建立或关闭时，接收状态清空；同 token 的重复 BEGIN 不清空状态。

`target_motor_rpm` 是**电机轴机械转速请求**，单位 RPM、有符号；`0x8000` 保留为无效值，禁止用于请求。正方向定义为对应侧履带前进，但实际电机相序/Hall方向在目标板和实机校准前不得假设已验证。上位机把策略给出的左/右归一化履带速度分别换算成电机轴 RPM；本板协议不接受归一化策略动作，也不实现轨道换算、差速混合或转矩请求。

`ttl_10ms` 范围 1–10，表示请求在接收后有效 `10..100 ms`。到达 TTL 边界（接收年龄 `>= TTL`）即无效；不能继续保持最后一条速度目标。过期的具体执行由目标固件按既有安全状态处理；本合同不提供 ARM 授权，不要求或实现 PWM。

## 电机反馈、质量与配对

每个驱动器的状态帧和质量帧通过同一 `sample_seq:u16` 原子配对。序号按样本递增并自然回绕；上位机只合并序号相同的一对帧，不能把新旧帧交叉拼接。状态字段含义：

- `mechanical_rpm:i16` 是电机轴实际机械转速，RPM，不是履带线速度。`0x8000` 表示该项无效。
- `Iq_cA:i16` 是有符号 q 轴电流，分辨率 0.01 A；换算 `Iq_A = Iq_cA / 100.0`。`0x8000` 表示该项无效。该量不能称为电池电流或电机转矩。
- 若质量位 `RPM_VALID` 或 `IQ_VALID` 为 1，对应字段不得是 `0x8000`；若为 0，对应字段必须发 `0x8000`。

质量位定义如下。`LOW_SPEED_OR_REVERSAL_DEGRADED` 是低速/反向切换下的质量警告，**本身不清除** `RPM_VALID` 或 `IQ_VALID`；上位机按各自 measurement-valid 位判断数值是否可用。

| 位 | 名称 | 含义 |
|---:|---|---|
| 0 | `HALL_VALID` | Hall 输入/状态当前可信 |
| 1 | `RPM_VALID` | 此样本机械 RPM 有效 |
| 2 | `IQ_VALID` | 此样本有符号 Iq 有效 |
| 3 | `ELECTRICAL_ANGLE_VALID` | 此样本电角度可用 |
| 4 | `LOW_SPEED_OR_REVERSAL_DEGRADED` | 低速或反向切换性能降级警告；不等价于测量无效 |
| 5 | `LOCAL_LIMIT_ACTIVE` | 本地速度/电流/功率限制正在介入 |
| 6 | `FAULT_LATCHED` | 本地锁存故障存在 |
| 7 | `APPLIED_COMMAND_VALID` | `applied_command_seq` 表示确实被本地控制环接收的命令 |

若 `APPLIED_COMMAND_VALID=0`，`applied_command_seq` 必须为 `0xFF`；为 1 时 `0xFF` 也可作为有效序号。开始新会话或关闭会话时，应用命令状态必须无效，避免把上一会话同值序号误认为已应用。

`device_tick_ms_low16` 是设备本地毫秒计数低 16 位，65.536 s 回绕，只能用于同一设备的相邻样本间隔计算，不能当成跨节点绝对时间。上位机为每个状态/质量帧记录本地单调接收时刻；两帧各自年龄均不超过 100 ms 且 `sample_seq` 相同才组成可用反馈对。任一帧接收年龄超过 100 ms 即将该侧整对反馈标为 stale/无效。不要用设备 tick 代替上位机 stale 时间。

## 与策略反馈 schema 的映射

上位机按根模块 `gimbal-imu-drive-feedback-v1` 构造策略观测。每侧的本协议电机值按固定次序组成两元素数组 `[left, right]`：`Iq_A[2]` 为 A，`rpm[2]` 为电机轴机械 RPM；每侧保留自己的 `sample_seq`、质量位和上位机单调接收时间，之后才应用 schema 的 validity/stale 规则。云台的两轴实测角度 `q[2]` 用 rad，实测转速 `qd[2]` 用 rad/s；IMU 由上位机串口另行提供 `accel[3]` m/s²、`gyro[3]` rad/s、`mag_counts[3]` 为 ATK 原始有符号计数（厂家资料未确认 μT/计数比例）、`Euler[3]` rad、`quat_xyzw[4]`。气压和海拔不进入该 schema。动作指令不能冒充云台实测角速度，控制请求不能冒充反馈值。

## 文件与验证

- `速度反馈接口.h/.c`：纯 C11 帧编解码、CRC、会话/序号/TTL 状态和反馈配对。
- `速度反馈接口测试.c`：主机端边界、CRC、序号、超时、会话和配对测试。
- `golden_vectors.json`：供 Python adapter 等互通实现复用的固定 CAN ID、payload 与 CRC 样例。
- `运行主机测试.ps1`：用本机 GCC 编译严格 C11 测试并运行；二进制只写入临时目录。

主机测试通过只证明这份纯 C codec 的自洽性和固定向量互通，不证明 G431 编译、HAL、CAN收发、FOC、传感标定、保护动作、速度闭环、真实状态发送或实机运行。增加或改变帧定义时同步更新 golden vectors，并由上位机 Python adapter 使用同一组向量进行独立解析测试。
